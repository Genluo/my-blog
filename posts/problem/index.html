1. 性能相关#

1.1 慢查询问题：数据库查询优化、索引设计#

问题描述： 随着数据量增长，部分 SQL 查询响应时间从毫秒级退化到秒级甚至更长，直接拖慢接口响应，严重时导致数据库 CPU 打满、连接堆积，进而引发服务不可用。

常见原因：

  • 缺少必要索引或索引失效（如对索引列使用函数、隐式类型转换、前导模糊查询 LIKE '%xxx'）
  • 查询未命中覆盖索引，产生大量回表操作
  • 联合索引列顺序不当，违反最左前缀原则
  • 单表数据量过大（千万级以上），B+ 树层级增加导致 IO 次数上升
  • 复杂 JOIN、子查询导致临时表和文件排序

解决方案：

  • 开启慢查询日志（slow_query_log），通过 EXPLAIN / EXPLAIN ANALYZE 分析执行计划，关注 type、rows、Extra 等关键字段
  • 根据查询模式设计合理索引：高选择性列优先、覆盖索引减少回表、联合索引遵循最左前缀
  • 避免 SELECT *，只查询需要的列；将复杂查询拆分为多次简单查询
  • 引入读写分离，将分析型查询路由到从库
  • 超大表考虑分库分表或归档历史数据

1.2 N+1 查询问题：ORM 使用不当导致的性能问题#

问题描述： 在使用 ORM（如 Hibernate、MyBatis、Django ORM）查询关联数据时，先执行 1 次查询获取主表列表，再对列表中每条记录分别执行 1 次关联查询，总共产生 N+1 次数据库访问，导致接口延迟随数据量线性增长。

常见原因：

  • ORM 默认使用懒加载（Lazy Loading），在遍历集合时触发逐条查询
  • 开发者未意识到 ORM 在循环中自动发起 SQL
  • 缺乏 SQL 审计机制，问题在开发环境不易暴露（数据量小）

解决方案：

  • 使用 Eager Loading / Join Fetch 一次性加载关联数据（如 JPA 的 @EntityGraph、JOIN FETCH）
  • 使用批量加载策略（如 Hibernate 的 @BatchSize，MyBatis 的 <collection> 嵌套查询改为 JOIN）
  • 在应用层手动做批量 ID 查询：先收集所有关联 ID，一次 IN 查询获取全部关联数据，再在内存中组装
  • 引入 SQL 监控（如 p6spy、Druid 监控），在开发/测试阶段发现 N+1 问题
  • Code Review 时关注循环内的数据库访问模式

1.3 大数据量分页：深度分页性能下降#

问题描述： 使用 LIMIT offset, size 进行分页时，当 offset 值很大（如第 10000 页），数据库需要先扫描并丢弃前 offset 条记录，导致查询耗时随页码增加而线性增长。百万级数据的深度分页可能需要数秒甚至超时。

常见原因：

  • LIMIT 1000000, 20 实际需要扫描 1000020 行，前 1000000 行全部丢弃
  • 即使有索引，大 offset 仍需要大量的索引扫描和回表操作
  • 业务层未对分页深度做限制

解决方案：

  • 游标分页（Keyset Pagination）： 基于上一页最后一条记录的有序字段（如自增 ID 或时间戳）进行查询：WHERE id > last_id ORDER BY id LIMIT 20，避免 offset 扫描
  • 延迟关联： 先通过覆盖索引查出主键 ID 列表，再用 ID 列表回表查完整数据：SELECT * FROM t INNER JOIN (SELECT id FROM t ORDER BY x LIMIT 1000000, 20) AS tmp ON t.id = tmp.id
  • 搜索引擎： 对于全文检索类分页场景，使用 Elasticsearch 的 search_after 机制
  • 业务层限制： 限制最大可访问页码，或只提供"上一页/下一页"而不提供跳页功能
  • 预计算热点分页数据，放入缓存

1.4 连接池耗尽：数据库/Redis 连接管理不当#

问题描述： 应用获取数据库或 Redis 连接后未及时归还，或并发量超过连接池上限，导致后续请求因获取不到连接而阻塞或报错（如 Cannot get a connection, pool error: Timeout waiting for idle object），最终服务不可用。

常见原因：

  • 连接泄漏：获取连接后因异常未在 finally 中释放，或事务未正确提交/回滚
  • 慢查询长时间占用连接，导致可用连接数减少
  • 连接池参数配置不合理：最大连接数过小、等待超时过长
  • 突发流量超出连接池承载能力
  • 连接健康检查缺失，池中存在大量失效连接

解决方案：

  • 确保连接使用 try-with-resources 或框架自动管理，杜绝连接泄漏
  • 合理设置连接池参数：maxActive（最大连接数）、maxWait（最大等待时间）、minIdle（最小空闲连接数）
  • 开启连接池监控（如 Druid 监控面板、HikariCP Metrics），及时告警
  • 配置连接有效性检测（testOnBorrow、validationQuery）和空闲连接回收策略
  • 从根源解决慢查询问题，缩短连接占用时间
  • 读写分离和分库分表分散连接压力

1.5 热点问题：Hot Key、热点数据访问#

问题描述： 系统中某些特定数据（如爆款商品详情、明星微博、秒杀活动页）被大量请求集中访问，导致承载该数据的单个缓存节点或数据库分片成为瓶颈。Redis 单节点 QPS 可能被打到 10 万+，出现响应变慢、连接拒绝甚至节点宕机，进而引发缓存穿透或雪崩。

常见原因：

  • 业务天然存在热点：爆款商品、热搜话题、秒杀活动等少数 Key 占据绝大部分流量
  • Redis Cluster 模式下，同一个 Key 的所有请求只会路由到同一个 slot 所在的节点，无法利用集群的横向扩展能力
  • 缓存过期瞬间大量请求穿透到数据库（缓存击穿）
  • 数据库层面某张表或某行数据被高频读写，行锁竞争激烈

解决方案：

  • 热点 Key 发现：
    • Redis 4.0+ 使用 redis-cli --hotkeys 或 OBJECT FREQ 命令（需开启 LFU 淘汰策略）发现热点 Key
    • 客户端侧统计访问频次，实时上报热点 Key
    • 通过监控系统（如 Prometheus + Redis Exporter）识别 QPS 异常的 Key
  • 本地缓存（L1 Cache）： 在应用层引入本地缓存（如 Caffeine、Guava Cache）缓存热点数据，请求不再打到 Redis，大幅降低远程访问压力。需注意本地缓存一致性和过期策略
  • Key 分散（读副本）： 将热点 Key 复制多份（如 product:123 拆分为 product:123:1 ~ product:123:16），读请求随机路由到不同副本，将压力分散到多个 Redis 节点
  • 缓存击穿防护： 对热点 Key 设置永不过期 + 后台异步刷新；或使用互斥锁（Redis SETNX）保证只有一个请求回源数据库，其他请求等待或返回旧数据
  • 读写分离： Redis 使用主从架构 + 读写分离，读请求分散到多个从节点
  • 数据库层面： 对热点行的读请求走缓存兜底，写请求使用队列串行化；必要时将热点数据单独分库，避免影响普通数据

与 5.1 数据倾斜的区别： 数据倾斜关注的是分库分表后数据存储分布不均（静态视角），热点问题关注的是少数数据访问流量集中导致的单点瓶颈（动态视角）。两者可能同时出现——热点数据恰好又落在倾斜的大分片上，会加剧问题。

2. 并发问题#

2.1 超卖问题：库存扣减、秒杀场景#

问题描述： 在高并发的库存扣减或秒杀场景中，多个请求同时读取到相同的库存余量，各自判断库存充足后分别执行扣减，导致最终库存变为负数，即"超卖"。这是典型的 check-then-act 竞态条件。

常见原因：

  • 先查询库存再更新库存，两步操作非原子性
  • 数据库没有加锁或使用的锁粒度不当
  • 分布式环境下单机锁无法保证互斥

解决方案：

  • 数据库乐观锁： UPDATE stock SET count = count - 1 WHERE product_id = ? AND count > 0，利用数据库行锁保证原子性，通过影响行数判断是否扣减成功
  • Redis 原子操作： 将库存预热到 Redis，使用 Lua 脚本原子地执行判断+扣减：if redis.call('get', key) > 0 then redis.call('decr', key) end
  • 分布式锁： 使用 Redis（Redisson）或 ZooKeeper 分布式锁串行化扣减操作，适用于并发量适中的场景
  • 消息队列削峰： 秒杀请求先入队，后端按序消费，将并发转为串行处理
  • 分段库存： 将总库存拆分到多个桶（如 10 个），每个桶独立扣减，降低锁竞争

2.2 重复提交：表单重复提交、接口幂等性#

问题描述： 用户因网络抖动、页面卡顿等原因多次点击提交按钮，或者客户端因超时重试，导致同一业务操作被执行多次，产生重复订单、重复支付、重复数据等问题。

常见原因：

  • 前端未做防重复点击处理
  • 后端接口缺乏幂等性保护
  • 网络超时后客户端自动重试
  • 消息队列消费端未做幂等消费

解决方案：

  • 前端防抖： 提交按钮点击后立即置灰/禁用，等待响应后恢复
  • Token 机制： 进入页面时向后端申请一个唯一 Token，提交时携带该 Token，后端基于 Token 做去重（Redis SETNX），用完即删
  • 唯一约束： 在数据库层面利用唯一索引防止重复数据（如订单号唯一索引）
  • 幂等设计： 接口设计时天然支持幂等——SET 操作天然幂等；INSERT 操作加唯一键约束；UPDATE 操作使用绝对值而非增量
  • 状态机： 业务流转使用状态机模型，重复请求因状态不满足前置条件而被拒绝
  • 去重表： 将已处理的请求唯一标识（如请求 ID）记录到去重表，后续请求先查询是否已处理

2.3 死锁：数据库死锁、分布式死锁#

问题描述： 两个或多个事务/线程互相持有对方需要的锁资源，形成循环等待，所有相关事务均无法继续执行。数据库层面死锁会导致事务被回滚；分布式场景下的死锁则可能导致服务长时间阻塞。

常见原因：

  • 多个事务以不同顺序访问同一组资源（如事务 A 先锁行 1 再锁行 2，事务 B 先锁行 2 再锁行 1）
  • 间隙锁（Gap Lock）与插入意向锁冲突，在 RR 隔离级别下常见
  • 长事务持有锁时间过长，增加死锁概率
  • 分布式锁嵌套使用，多服务间形成循环依赖

解决方案：

  • 统一加锁顺序： 所有事务按照相同的顺序访问资源（如统一按主键升序加锁）
  • 缩短事务： 减少事务中的操作步骤，尤其避免在事务中进行 RPC 调用或耗时操作
  • 降低隔离级别： 在可接受的范围内将事务隔离级别从 RR 降为 RC，减少间隙锁
  • 死锁检测： MySQL InnoDB 自带死锁检测（innodb_deadlock_detect），自动回滚代价最小的事务；应用层做好重试机制
  • 超时机制： 设置锁等待超时时间（innodb_lock_wait_timeout），超时后主动放弃
  • 分布式场景： 使用带超时的分布式锁，避免无限等待；引入全局锁顺序协议

2.4 线程安全：共享资源竞争#

问题描述： 多线程并发访问共享可变资源（如全局变量、共享集合、缓存对象）时，由于缺少同步机制，导致数据不一致、脏读、丢失更新等问题。问题往往难以复现，在高并发下才暴露。

常见原因：

  • 使用 HashMap、ArrayList 等非线程安全集合在多线程间共享
  • SimpleDateFormat 等非线程安全工具类作为成员变量或静态变量
  • Spring 默认 Bean 是单例（Singleton），如果在 Bean 中使用了可变成员变量则存在线程安全问题
  • 复合操作（check-then-act、read-modify-write）未保证原子性

解决方案：

  • 使用线程安全容器： ConcurrentHashMap 替代 HashMap，CopyOnWriteArrayList 替代 ArrayList
  • 局部变量优先： 将状态放在方法局部变量或 ThreadLocal 中，避免共享
  • 不可变对象： 使用不可变类（如 DateTimeFormatter 替代 SimpleDateFormat）
  • 同步机制： 必要时使用 synchronized、ReentrantLock、ReadWriteLock 保护临界区
  • 原子类： 使用 AtomicInteger、AtomicReference、LongAdder 等 CAS 原子操作替代加锁
  • 无状态设计： Spring Bean 中避免可变成员变量，保持无状态

3. 数据一致性#

3.1 缓存一致性：缓存与数据库数据不一致#

问题描述： 在使用缓存（如 Redis）加速读取的架构中，当数据库数据发生更新时，缓存中的旧数据未及时同步，导致用户读到过期数据。反之，如果先删缓存再更新数据库，并发读请求可能将旧数据重新写入缓存。

常见原因：

  • 先更新数据库再删除缓存，删除缓存失败导致脏数据残留
  • 先删除缓存再更新数据库，并发请求在数据库更新完成前将旧数据重新加载到缓存
  • 缓存与数据库操作不在同一事务中，无法保证原子性
  • 主从复制延迟导致从库读到旧数据并写入缓存

解决方案：

  • Cache Aside Pattern（旁路缓存策略）： 读时先查缓存，未命中则查数据库并回填缓存；写时先更新数据库，再删除缓存
  • 延迟双删： 写操作先删缓存、更新数据库、延迟一段时间（如 500ms，大于主从复制延迟）后再次删除缓存
  • 基于 Binlog 的异步更新： 通过 Canal 等组件监听 MySQL Binlog，异步删除或更新缓存，保证最终一致性
  • 设置合理的 TTL： 缓存设置过期时间作为兜底，即使出现不一致也能在 TTL 到期后自动修复
  • 加锁/队列串行化： 对同一个 key 的写操作串行化，避免并发导致的不一致

3.2 分布式事务：跨服务/跨数据库的事务处理#

问题描述： 在微服务架构中，一个业务操作可能涉及多个服务或多个数据库的数据变更（如下单涉及订单服务、库存服务、支付服务），传统的单机事务无法跨服务保证 ACID，部分服务成功部分失败会导致数据不一致。

常见原因：

  • 微服务拆分后，原本在同一数据库中的事务操作被分散到多个服务
  • 分库分表后跨库操作失去单机事务保障
  • 网络不可靠，RPC 调用可能超时或失败，导致部分操作成功部分失败

解决方案：

  • 本地消息表（事务消息）： 在本地事务中同时写入业务数据和消息记录，定时任务扫描未发送的消息并投递，下游消费后反馈确认。保证最终一致性
  • TCC（Try-Confirm-Cancel）： 将操作拆分为三个阶段——Try（资源预留）、Confirm（提交）、Cancel（回滚），每个参与者实现这三个接口。适用于对一致性要求高且实时性要求强的场景
  • Saga 模式： 将长事务拆分为一系列本地事务，每个本地事务有对应的补偿操作。如果某步失败，依次执行前面步骤的补偿操作回滚
  • Seata 框架： 使用 Seata 的 AT 模式，通过全局锁和 undo log 实现自动补偿，对业务代码侵入性低
  • 最大努力通知： 适用于对一致性要求不高的场景（如通知类），通过重试机制最大努力保证通知送达
  • 设计原则： 优先考虑能否通过业务设计避免分布式事务；能用最终一致性就不追求强一致性

3.3 数据同步延迟：主从复制延迟、消息队列延迟#

问题描述： 在读写分离或消息驱动架构中，数据从主库到从库、从生产者到消费者的同步存在延迟。用户执行写操作后立即读取，可能从从库读到旧数据（“刚写完就查不到”）；消息堆积时消费延迟可能从毫秒级退化到分钟级甚至小时级。

常见原因：

  • 主从复制为异步模式，主库写入到从库应用存在天然延迟
  • 主库写入压力大，大事务（如批量更新）导致 Binlog 传输和回放耗时
  • 消息队列消费者处理能力不足或消费逻辑过重，导致消息堆积
  • 网络带宽瓶颈或跨机房部署增加传输延迟

解决方案：

  • 强制走主库： 对于写后读（Read After Write）场景，在写操作后的短时间窗口内强制路由到主库读取
  • 半同步复制： 将 MySQL 复制模式升级为半同步（Semi-sync），至少一个从库确认接收到 Binlog 后主库才返回成功
  • GTID + 并行复制： 启用 GTID 追踪复制位点，开启多线程并行回放提升从库追赶速度
  • 消息队列扩容： 增加消费者实例数和分区数，提升消费吞吐量；优化消费逻辑，异步化耗时操作
  • 监控告警： 监控主从延迟（Seconds_Behind_Master）和消息堆积量，设置阈值告警
  • 业务补偿： 提供数据刷新按钮或提示"数据同步中"，降低用户感知

4. 稳定性问题#

4.1 雪崩效应：依赖服务故障导致级联失败#

问题描述： 微服务架构中，某个下游服务出现故障（如响应超慢或完全不可用），导致调用方线程被阻塞、连接池耗尽，进而影响调用方自身对外提供服务的能力。这种故障像滚雪球一样沿着调用链向上传播，最终导致整个系统瘫痪。

常见原因：

  • 下游服务响应超慢（非快速失败），调用方线程长时间等待
  • 缺少超时控制和熔断机制，故障服务持续接收请求
  • 服务间强依赖，缺少降级方案
  • 共享线程池/连接池，一个慢接口拖垮整个服务

解决方案：

  • 熔断器模式（Circuit Breaker）： 使用 Hystrix / Sentinel / Resilience4j 实现熔断，当失败率超过阈值自动打开熔断器，快速失败不再请求下游，一段时间后半开尝试恢复
  • 线程池隔离 / 信号量隔离： 为不同的下游服务分配独立的线程池或信号量，防止一个慢服务耗尽所有线程
  • 超时控制： 为所有外部调用设置合理的超时时间（连接超时 + 读超时），超时后快速失败
  • 降级策略： 熔断触发后返回降级数据（缓存数据、默认值、友好提示），保证核心功能可用
  • 异步化： 将非核心依赖改为异步调用（消息队列），解耦服务间的同步依赖

4.2 服务降级与熔断：异常流量处理#

问题描述： 当系统面临突发大流量（如促销活动、爬虫攻击）或部分组件异常时，如果不采取保护措施，系统会因资源耗尽而全面崩溃。需要有选择地放弃部分非核心功能，保障核心业务链路的可用性。

常见原因：

  • 缺乏过载保护机制，系统在高压下无差别处理所有请求
  • 核心与非核心功能耦合，非核心功能异常拖垮核心功能
  • 缺少预案，突发情况下无法快速应对

解决方案：

  • 自动降级： 基于响应时间、错误率等指标自动触发降级策略，如关闭推荐算法返回热门列表、关闭评论功能、返回缓存数据
  • 手动降级（开关预埋）： 通过配置中心（如 Nacos、Apollo）预埋功能开关，紧急情况下手动关闭非核心功能
  • 熔断策略配置： 合理配置熔断阈值（错误率、慢调用比例）、熔断时长、半开试探次数
  • 流量分级： 区分核心流量和非核心流量，优先保障核心流量的资源分配
  • 预案演练： 定期进行故障演练（Chaos Engineering），验证降级策略的有效性
  • 监控大盘： 建立全链路监控，实时感知系统状态，为决策提供依据

4.3 限流策略：防止系统过载#

问题描述： 系统的处理能力是有上限的，当入口流量超过系统承载能力时，如果不进行限流，所有请求的响应质量都会下降，最终导致系统崩溃。需要在入口处对超出处理能力的请求进行拒绝或排队，保护后端服务。

常见原因：

  • 系统未设置限流措施，任何量级的请求都直接打到后端
  • 限流阈值设置不合理（过高或过低）
  • 单一限流维度无法覆盖所有攻击面（如只限制了 IP 维度，未限制用户维度）

解决方案：

  • 常见限流算法：
    • 固定窗口计数器： 实现简单，但存在窗口边界突发问题
    • 滑动窗口计数器： 解决固定窗口边界突发问题，更平滑
    • 漏桶算法（Leaky Bucket）： 以恒定速率处理请求，平滑突发流量
    • 令牌桶算法（Token Bucket）： 允许一定程度的突发流量，Guava RateLimiter 使用此算法
  • 多层限流：
    • 网关层（Nginx / API Gateway）：IP 限流、URL 限流
    • 应用层（Sentinel / Guava）：接口级、用户级、业务级限流
    • 中间件层：Redis + Lua 实现分布式限流
  • 限流维度： IP、用户 ID、接口、业务参数等多维度组合
  • 限流响应： 返回 HTTP 429 状态码和友好提示，告知客户端稍后重试（可携带 Retry-After 头）

4.4 OOM 问题：内存泄漏、大对象处理#

问题描述： Java 应用运行过程中出现 OutOfMemoryError，导致服务不可用或被 OOM Killer 杀死。OOM 可能发生在堆内存、元空间、直接内存等不同区域，表现为进程崩溃、频繁 Full GC 或响应极慢。

常见原因：

  • 内存泄漏：对象被意外引用无法被 GC 回收（如静态集合持续添加、监听器/回调未注销、ThreadLocal 未清理）
  • 大对象处理：一次性加载大量数据到内存（如全表查询、大 Excel 导入、大 JSON 解析）
  • 元空间溢出：动态生成大量类（如 CGLIB 动态代理、Groovy 脚本编译）
  • 线程过多：每个线程默认占用 1MB 栈空间，大量线程创建导致 OOM
  • 堆外内存泄漏：NIO DirectByteBuffer 未释放

解决方案：

  • 内存泄漏排查： 配置 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path，使用 MAT / VisualVM / Arthas 分析 Heap Dump，定位泄漏对象及其 GC Root 引用链
  • 大数据量处理： 使用流式处理替代全量加载——数据库用游标查询 / 分批查询，Excel 用 EasyExcel 的 SAX 模式，JSON 用 Jackson Streaming API
  • JVM 参数调优： 根据实际情况调整 -Xmx（最大堆）、-XX:MaxMetaspaceSize（最大元空间）、-XX:MaxDirectMemorySize（最大直接内存）
  • 代码规范： 避免在静态集合中无限制添加元素；使用 try-with-resources 确保资源释放；ThreadLocal 使用后及时 remove()
  • 线程池管理： 使用线程池替代直接创建线程，控制最大线程数

5. 数据问题#

5.1 数据倾斜：分库分表后数据分布不均#

问题描述： 分库分表后，由于分片键选择不当或数据本身的分布特征，导致大量数据集中在少数几个分片上，形成"热点"。热点分片承受远高于其他分片的读写压力，出现性能瓶颈，而其他分片资源闲置，违背了分库分表的初衷。

常见原因：

  • 分片键选择不当：如按地区分片但大量用户集中在某几个城市；按商家 ID 分片但头部商家数据量远超其他商家
  • 时间维度的倾斜：按日期分表时，当天的表承受所有写入压力
  • 自增 ID 作为分片键：新数据集中写入最后一个分片
  • 哈希算法不均匀

解决方案：

  • 合理选择分片键： 选择数据分布均匀且查询频繁的字段作为分片键（如用户 ID 取模），避免使用业务含义过强的字段
  • 一致性哈希： 使用一致性哈希算法，既保证数据均匀分布，又降低扩容时的数据迁移量
  • 二次分片： 对热点数据进行二次拆分（如大商家的数据再按时间拆分）
  • 基因法： 将分片因子嵌入到业务 ID 中（如订单 ID 末几位包含用户 ID 的哈希），使相关数据落在同一分片
  • 监控与调整： 定期监控各分片数据量和 QPS，发现倾斜后及时调整分片策略或迁移数据

5.2 跨库查询/Join：分库后的关联查询#

问题描述： 分库分表后，原本在同一数据库中可以通过 JOIN 完成的关联查询，现在数据分散在不同的物理库中，无法直接 SQL JOIN。这是分库分表最大的痛点之一，严重影响查询灵活性。

常见原因：

  • 分库分表设计时未充分考虑关联查询场景
  • 业务发展导致出现跨库关联需求
  • 报表/统计类查询天然需要跨库聚合

解决方案：

  • 冗余数据： 将频繁关联的字段冗余到主表中，避免跨库 JOIN。以空间换时间，需权衡数据一致性
  • 全局表（广播表）： 对于字典表、配置表等小表，在每个分片中都复制一份，可与分片表直接 JOIN
  • 应用层组装： 分别查询各库数据，在应用层通过代码进行关联组装（类似 Map-Reduce 思路）
  • 中间件支持： 使用 ShardingSphere 等中间件的跨库查询能力，自动进行查询路由和结果合并（但性能可能不理想）
  • 搜索引擎同步： 将需要复杂查询的数据同步到 Elasticsearch，利用其强大的查询能力满足多维检索需求
  • CQRS 模式： 命令（写）走分片数据库，查询（读）走独立的查询库（宽表或搜索引擎），读写分离各自优化

5.3 数据迁移：版本升级、扩容时的数据迁移#

问题描述： 在系统升级（如表结构变更、分片规则调整）或扩容（如增加数据库节点）时，需要将大量存量数据迁移到新的存储结构中。迁移过程中需要保证数据完整性、一致性，同时尽量减少对线上服务的影响（甚至要求零停机）。

常见原因：

  • 业务发展导致表结构需要重构
  • 分库分表扩容，需要重新哈希和数据迁移
  • 更换数据库类型（如 MySQL 迁移到 TiDB）
  • 历史数据归档

解决方案：

  • 双写方案： 新老库同时写入，增量数据保持一致；全量存量数据通过离线工具迁移；迁移完成后验证一致性，切换读取到新库，最后关闭老库写入
  • Binlog 同步： 使用 Canal / DTS 等工具监听老库 Binlog，实时同步到新库，延迟极小
  • 分批迁移： 按主键范围或时间范围分批迁移，每批次迁移后验证数据一致性，出问题可快速止损
  • 灰度切流： 迁移完成后不立即全量切换，先灰度一小部分流量到新库，观察无误后逐步放量
  • 回滚预案： 迁移期间保持老库可用，准备好一键回滚方案
  • 数据校验： 迁移后通过对账工具逐行比对新老库数据，确保一致性（数据量、关键字段校验）

6. 网络与 IO#

6.1 超时设置：合理的超时时间配置#

问题描述： 服务间调用或访问外部资源时，如果超时时间配置不合理——过长会导致线程长时间阻塞，资源耗尽引发雪崩；过短会导致正常请求被误杀，成功率下降。缺少超时设置则可能导致线程无限等待。

常见原因：

  • 使用框架默认超时配置（往往过长或无超时）
  • 所有接口使用统一的超时时间，未区分快慢接口
  • 多层调用链的超时时间未统一规划，下游超时时间大于上游

解决方案：

  • 分层设置超时：
    • 连接超时（Connect Timeout）：建议 1-3 秒，连接建立不应太久
    • 读超时（Read/Socket Timeout）：根据下游接口 P99 响应时间设置，通常为 P99 的 2-3 倍
    • 整体超时（Overall Timeout）：包含重试在内的总超时，需小于上游调用方的超时时间
  • 链路超时递减： 调用链上游到下游的超时时间应递减，如网关 5s → A 服务 3s → B 服务 1s，避免上游已超时但下游还在处理
  • 不同接口差异化配置： 核心接口可适当放宽，非核心接口收紧；读接口与写接口分别设置
  • 超时后的处理： 超时后及时释放资源，对可重试的操作进行有限次重试（注意幂等性），不可重试的快速返回错误
  • 定期回顾： 监控接口响应时间分布，定期调整超时配置

6.2 长连接管理：WebSocket、长轮询#

问题描述： WebSocket 和长轮询等长连接场景下，服务端需要维护大量持久连接。每个连接占用文件描述符和内存资源，连接异常断开后如果未正确处理，会导致资源泄漏和连接数虚高；此外还面临负载均衡、消息推送等独特挑战。

常见原因：

  • 未设置心跳检测，无法感知连接已断开（半开连接问题）
  • 客户端异常退出未触发关闭事件，服务端连接未释放
  • 长连接服务无法使用常规的轮询负载均衡，连接分布不均
  • 单机连接数超过文件描述符限制

解决方案：

  • 心跳机制： 定期发送 Ping/Pong 帧检测连接存活，超时未响应则主动断开释放资源
  • 重连策略： 客户端实现指数退避重连机制，避免服务端重启时大量连接同时重连（惊群效应）
  • 连接生命周期管理： 设置连接最大空闲时间，超时自动关闭；维护连接注册表，方便查询和管理
  • 资源限制： 调整系统 ulimit 和内核参数（fs.file-max、net.core.somaxconn），提升单机连接上限
  • 负载均衡： 使用基于连接数的负载均衡策略（Least Connections）；或引入连接迁移机制
  • 集群消息推送： 使用 Redis Pub/Sub 或消息队列广播消息到所有服务实例，由持有目标连接的实例推送给客户端

6.3 大文件上传/下载：分片、断点续传#

问题描述： 上传或下载大文件（几百 MB 到数 GB）时，单次 HTTP 请求容易超时、占用大量内存和带宽，且一旦中途失败需要从头开始，用户体验极差。服务端一次性接收整个文件也会导致内存溢出。

常见原因：

  • 使用常规文件上传方式，整个文件加载到内存
  • 网络不稳定导致传输中断，缺乏续传机制
  • Nginx/网关的请求体大小限制
  • 服务端未做流式处理，导致 OOM

解决方案：

  • 分片上传：
    • 前端将文件切割为固定大小的分片（如 5MB），并行或顺序上传各分片
    • 服务端接收分片并暂存（磁盘/对象存储），全部分片上传完成后合并
    • 每个分片携带分片序号和文件 MD5，服务端校验完整性
  • 断点续传：
    • 上传前先查询已上传的分片列表（通过文件 MD5 标识）
    • 客户端跳过已上传的分片，仅上传缺失部分
    • 利用 HTTP Range 头实现下载断点续传
  • 秒传： 上传前先发送文件 MD5 到服务端校验，如果已存在相同文件则直接返回成功
  • 流式处理： 服务端使用流式 API 接收文件，不将整个文件加载到内存
  • 对象存储： 使用 OSS / S3 的分片上传 API，利用云服务的能力处理大文件
  • 配置调整： 调大 Nginx client_max_body_size、Tomcat maxSwallowSize 等参数

7. 代码质量#

7.1 循环依赖：服务间、模块间循环依赖#

问题描述： 模块 A 依赖模块 B，模块 B 又依赖模块 A，形成循环依赖。在 Spring 中表现为 Bean 之间的循环引用导致启动失败（Spring Boot 2.6+ 默认禁止循环依赖）；在微服务中表现为服务间互相调用形成环路，增加系统复杂性和故障概率。

常见原因：

  • 代码职责划分不清，模块边界模糊
  • 为了方便直接互相引用，缺乏分层设计
  • 服务拆分不合理，两个服务本应合并或抽取公共服务

解决方案：

  • 重新设计分层： 引入中间层打破循环——抽取公共模块 / 接口层，让两个模块都依赖公共层而非互相依赖
  • 依赖倒置（DIP）： 通过接口抽象解耦，模块 A 定义接口，模块 B 实现接口，A 只依赖自己定义的接口
  • 事件驱动： 将同步调用改为事件发布/订阅，A 发布事件，B 监听事件处理，消除直接依赖
  • Spring 中的处理： 使用 @Lazy 延迟加载打破循环（临时方案）；重构为 Setter 注入替代构造器注入（不推荐长期方案）
  • 微服务间： 引入消息队列解耦互相调用；抽取第三方服务承接共用功能
  • 架构检查： 使用 ArchUnit 等工具在 CI 中检测循环依赖，防止引入

7.2 事务失效：Spring 事务不生效场景#

问题描述： 开发者使用了 @Transactional 注解，期望方法在事务中执行，但实际上事务并未生效——发生异常时数据没有回滚，导致数据不一致。这是 Spring 开发中最隐蔽的坑之一，因为代码表面上看不出问题。

常见原因及解决方案：

  • 方法非 public： Spring AOP 默认只代理 public 方法，private/protected/default 方法上的 @Transactional 不生效。→ 确保事务方法为 public
  • 自调用问题： 同一个类中方法 A 调用方法 B（B 有 @Transactional），由于未经过代理对象调用，事务不生效。→ 注入自身代理（@Autowired self）或使用 AopContext.currentProxy()，或将事务方法移到另一个 Bean
  • 异常类型不匹配： @Transactional 默认只对 RuntimeException 和 Error 回滚，受检异常（Checked Exception）不回滚。→ 配置 @Transactional(rollbackFor = Exception.class)
  • 异常被吞掉： 事务方法内部 catch 了异常但未重新抛出，Spring 感知不到异常，不触发回滚。→ catch 后重新抛出或手动 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()
  • 数据库引擎不支持事务： MySQL 的 MyISAM 引擎不支持事务。→ 确保表使用 InnoDB 引擎
  • 传播行为配置错误： 如 REQUIRES_NEW 会开启新事务，外层事务回滚不影响内层事务。→ 理解并正确使用事务传播行为

7.3 异常处理：异常吞噬、异常传播#

问题描述： 系统中异常处理不当——异常被 catch 后仅打印日志甚至完全忽略（吞噬异常），导致错误被隐藏、数据不一致且极难排查；或者异常未经恰当处理直接向上抛出，导致技术细节暴露给用户，甚至引发安全风险。

常见原因：

  • 为了"不报错"而在 catch 块中什么都不做或只打印日志
  • catch 了过于宽泛的异常类型（如 catch (Exception e)）
  • 异常信息不完整，丢失了原始异常的堆栈（如 throw new RuntimeException(e.getMessage()) 丢失了 cause）
  • 跨层异常传播不规范，底层实现细节泄漏到上层

解决方案：

  • 不要吞掉异常： catch 异常后必须做有意义的处理——记录日志并重新抛出、转换为业务异常、触发补偿逻辑等。绝不允许空 catch 块
  • 保留异常链： 转换异常时使用 throw new BusinessException("message", cause) 保留原始异常信息，便于排查
  • 精准捕获： catch 具体的异常类型而非 Exception，对不同异常做不同处理
  • 分层异常转换：
    • DAO 层：抛出数据访问异常（如 Spring 的 DataAccessException）
    • Service 层：转换为业务异常（如 OrderNotFoundException）
    • Controller 层：通过全局异常处理器（@ControllerAdvice）统一转换为友好的 API 响应
  • 全局异常处理器： 使用 @ControllerAdvice + @ExceptionHandler 统一处理未捕获异常，返回标准错误响应，避免堆栈信息泄漏
  • 日志规范： 记录异常时使用 log.error("message", e) 而非 log.error(e.getMessage())，确保完整堆栈被记录
