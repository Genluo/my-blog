服务端领域业务问题汇总

1. 性能相关 1.1 慢查询问题：数据库查询优化、索引设计 问题描述： 随着数据量增长，部分 SQL 查询响应时间从毫秒级退化到秒级甚至更长，直接拖慢接口响应，严重时导致数据库 CPU 打满、连接堆积，进而引发服务不可用。 常见原因： 缺少必要索引或索引失效（如对索引列使用函数、隐式类型转换、前导模糊查询 LIKE '%xxx'） 查询未命中覆盖索引，产生大量回表操作 联合索引列顺序不当，违反最左前缀原则 单表数据量过大（千万级以上），B+ 树层级增加导致 IO 次数上升 复杂 JOIN、子查询导致临时表和文件排序 解决方案： 开启慢查询日志（slow_query_log），通过 EXPLAIN / EXPLAIN ANALYZE 分析执行计划，关注 type、rows、Extra 等关键字段 根据查询模式设计合理索引：高选择性列优先、覆盖索引减少回表、联合索引遵循最左前缀 避免 SELECT *，只查询需要的列；将复杂查询拆分为多次简单查询 引入读写分离，将分析型查询路由到从库 超大表考虑分库分表或归档历史数据 1.2 N+1 查询问题：ORM 使用不当导致的性能问题 问题描述： 在使用 ORM（如 Hibernate、MyBatis、Django ORM）查询关联数据时，先执行 1 次查询获取主表列表，再对列表中每条记录分别执行 1 次关联查询，总共产生 N+1 次数据库访问，导致接口延迟随数据量线性增长。 常见原因： ORM 默认使用懒加载（Lazy Loading），在遍历集合时触发逐条查询 开发者未意识到 ORM 在循环中自动发起 SQL 缺乏 SQL 审计机制，问题在开发环境不易暴露（数据量小） 解决方案： 使用 Eager Loading / Join Fetch 一次性加载关联数据（如 JPA 的 @EntityGraph、JOIN FETCH） 使用批量加载策略（如 Hibernate 的 @BatchSize，MyBatis 的 <collection> 嵌套查询改为 JOIN） 在应用层手动做批量 ID 查询：先收集所有关联 ID，一次 IN 查询获取全部关联数据，再在内存中组装 引入 SQL 监控（如 p6spy、Druid 监控），在开发/测试阶段发现 N+1 问题 Code Review 时关注循环内的数据库访问模式 1.3 大数据量分页：深度分页性能下降 问题描述： 使用 LIMIT offset, size 进行分页时，当 offset 值很大（如第 10000 页），数据库需要先扫描并丢弃前 offset 条记录，导致查询耗时随页码增加而线性增长。百万级数据的深度分页可能需要数秒甚至超时。 ...
